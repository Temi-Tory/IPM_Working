\section{Introduction}
\label{sec:bg-intro}

Chapter~\ref{ch:main-intro} introduced three questions that can be asked of a process system
modelled as a directed acyclic graph, and named the method that answers each. This chapter
reviews those methods and the literature around them. Sections~\ref{sec:bg-reliability}
to~\ref{sec:bg-schedule} cover network reliability, network flow and scheduling in turn, with
attention to the exact methods and to where their cost comes from.
Section~\ref{sec:bg-uncertainty} reviews the representations available for uncertain inputs,
defines the two that this thesis uses, and records how each of the three literatures has
treated imprecision. Section~\ref{sec:bg-frameworks} examines the tools and methods that run
more than one of the three analyses on a single network, and Section~\ref{sec:bg-delivery}
the forms in which engineering analysis software reaches its users.
Section~\ref{sec:bg-language} notes the state of graph tooling in the languages the work could
have been written in. The chapter closes with the gap that the rest of the thesis addresses.

\section{Network Reliability Computation}
\label{sec:bg-reliability}

The reliability of a network in this work is the probability that the network performs its
function when its components can fail. For the kind of systems the framework addresses, the
function is delivery from a source to a node, so the quantity of interest is the probability that at least one path from a source to
the node has all of its components operating. Computing this quantity exactly is \#P-hard in
general \cite{valiant1979complexity,ball1986computational}, so every exact method is exponential
in some property of the network, and the methods differ in which property that is.

The earliest formulations are structural. A reliability block diagram arranges components in
series, parallel and $k$-out-of-$n$ groups, each of which has a closed-form system reliability
\cite{billinton1992network}. Fault trees and event trees build the failure mechanism explicitly
as a tree of logic gates \cite{xing2008fault}. Both are efficient as far as the failure logic
reduces to a tree or a series-parallel structure. However, both stop being efficient at the
same point, which is where routes in the network diverge and reconverge with shared components
upstream. This structure follows from the design of the system. A robust network provides
more than one route to the same destination, and two routes to one destination begin at a
common component. Hence the redundancy that makes a system worth analysing is also the
structure these formalisms cannot hold \cite{ouyang2014interdependent,buldyrev2010cascade}.

Graph-theoretic methods compute on the network directly. Since reaching a node is the union of
its path events, the minimal path sets and the minimal cut sets give the reliability exactly
once the union is made disjoint, and recursive decomposition improves on raw enumeration by
splitting the network into subproblems \cite{liu2012improved,kim2013network}. However, the
collections of paths and cuts grow combinatorially with the same redundancy that motivates the
analysis.
Series-parallel reduction collapses independent stretches of the network pair by pair
\cite{satyanarayana1985linear}, and where the network is not series-parallel, factoring
conditions on a single component and recurses on the working and failed cases until the
remainder becomes reducible \cite{moore1956reliable,satyanarayana1983factoring,page1988practical}.
Polygon-to-chain reductions widen what can be collapsed in one step beyond a plain series or
parallel pair \cite{wood1985polygon}. Tree decomposition generalises the idea to graphs that no
sequence of such reductions can collapse. The network is arranged into small overlapping bags
connected as a tree \cite{robertson1986graphminors}, and the cost of exact computation is then
bounded by the width of that decomposition, whatever the size of the graph. This is what makes
exact reliability feasible on networks as large as metropolitan transit systems
\cite{goharshady2020treewidth}. Monte Carlo simulation does not depend on structure and handles any network, but it is
not exact, and the sample count it needs grows large when failures are rare or the required
precision is high \cite{fishman1986comparison}.

Binary decision diagrams (BDDs) compile the Boolean structure function of the network into a
canonical decision graph on which reliability is a single traversal
\cite{bryant1986graph,rauzy1993new}. The approach handles systems with thousands of variables.
However, its cost is concentrated in the size of the diagram, which depends on the order in which the
variables are decided, and finding a good ordering is itself intractable in general
\cite{bryant2002ordered}. Reconvergent fan-out is the hard case for a diagram, since intermediate
nodes must remember which shared ancestors have already been decided, and on a densely
reconvergent network the construction can exhaust memory under one ordering while staying
compact under another. Diagram implementations store each distinct sub-diagram once, a technique
known as hash-consing \cite{ershov1958programming,filliatre2006hashconsing}, and the same
technique is used in Chapter~\ref{ch:diamond-module} for a different unit of structure.

The probabilistic-inference literature reaches the same computation from another direction.
Reachability from a source is marginal inference on a directed graphical model, and the exact
inference methods are conditioning and clustering. Cutset conditioning enumerates the states of
a set of nodes whose fixing renders the remaining structure singly connected
\cite{pearl1988probabilistic}, and the junction-tree algorithm clusters the network into a tree
of overlapping bags \cite{lauritzen1988local}. Both are exact and both cost exponential in a
width of the graph, the cutset size for the one and the treewidth for the other. Message
passing makes the same inference local and scalable when exactness is relaxed. The directed
probability propagation method of Tong and Tien is a reliability-specific variant that tracks
marginal and pairwise probabilities to approximate the dependence between paths
\cite{tong2019directed}. It gains scale at the cost of approximation error and of pairwise
bookkeeping that grows with the number of dependent interactions. Its sixteen-node benchmark
grid is used again in Chapter~\ref{ch:probability-toolkit}.

Every method in this section, from the block diagram to the junction tree, takes a single
number for each component probability. Section~\ref{sec:bg-uncertainty} will further discuss
this.

\section{Network Flow}
\label{sec:bg-flow}

Flow along capacitated edges is the oldest of the three analyses in its deterministic form.
The maximum-flow minimum-cut theorem of Ford and Fulkerson states that the largest amount that
can be sent from a source to a sink equals the smallest total capacity of any set of edges
whose removal separates them \cite{ford1956,ford1962}. Hence the theorem gives a certificate of optimality, the minimum cut, alongside the flow
itself, and the augmenting-path, blocking-flow and push-relabel families of algorithms that
followed all compute both. Two further results
from the same theory are used in Chapter~\ref{ch:capacity-toolkit}. A node with its own
capacity is handled by splitting it into an entry node and an exit node joined by an edge of
that capacity, which preserves the correspondence between flows in the two networks. Any
feasible flow decomposes into a set of source-to-sink path flows that sum to the total. The
minimum cuts of a network are not in general unique, and their structure is characterised by
the sets of nodes reachable from the source in the residual graph and reachable to the sink in
the reverse residual graph, between which every minimum cut lies. The Birnbaum importance of a
component, its marginal effect on system performance, was defined in the reliability setting
\cite{birnbaum1969} and carries over to flow as the marginal value of a unit of capacity.

Deterministic flow analysis does not address what happens when the capacities themselves are
uncertain. Two different approaches have been developed for this case. In robust
optimisation an uncertain capacity is treated adversarially: the capacity is taken from a set
of possible values, no probability is assigned within that set, and the network is evaluated
against the worst case in the set. The robust maximum-flow problem is solvable in polynomial
time, while the corresponding robust minimum-cut problem is NP-hard \cite{bertsimas2013robust}.
The stochastic-flow network reliability problem, introduced by
Doulliez and Jamoulle, holds each arc capacity as a discrete random variable and asks for the
probability that the network can deliver a stated demand, computed by decomposing the space of
feasible capacity configurations \cite{doulliez1972transportation}. The family of methods that
followed, state-space decomposition, boundary-point enumeration and sum-of-disjoint-products
techniques, mirrors the path and cut-set methods of Section~\ref{sec:bg-reliability} closely,
and the same formalism carries into project scheduling, where an activity's duration and cost
take the place of an arc's capacity states (Section~\ref{sec:bg-frameworks}).

\section{Scheduling on Networks}
\label{sec:bg-schedule}

The critical path method models a project as a network of activities and computes the longest
path through it. The project cannot finish earlier than that path allows, and the activities on it have no
room to slip. Every other activity carries a float, equal to how far it can slip before it
delays the project. The method and its float calculus date to the late 1950s
\cite{kelley1959critical}. The question of duration uncertainty was raised almost at once. PERT
replaced each fixed duration with a three-point estimate and a distributional assumption
\cite{malcolm1959pert}, and its descendants in modern practice replace the assumption with
Monte Carlo sampling.

A distribution-free treatment of the same uncertainty came much later. When each duration is
known only as an interval, the forward quantities remain easy, since the earliest completion of
every node is a monotone function of the durations and its bounds are found at the two corners
of the input box. However, the backward quantities change character. Deciding whether an activity is
possibly critical is NP-complete, and computing float bounds is NP-hard
\cite{chanas2002complexity}, even on planar networks \cite{chanas2003planar}. Exact methods
exist for latest starting times and for one of the two float bounds \cite{dubois2005floats},
the consolidated picture of what is and is not tractable is given by Fortin, Zieli\'{n}ski,
Dubois and Fargier \cite{fortin2010criticality}, and the recognised tractable class is the
series-parallel networks \cite{valdes1982seriesparallel}. The backward quantities are hard
because a float is the difference between two quantities, the project completion and the
completion forced through the activity, which are both monotone in the durations but share the
same inputs. Their difference is therefore not monotone, and the corner argument that works for
the forward quantities does not apply.

Furthermore, none of the machinery is specific to time. The forward recursion combines
incoming values and compounds them along edges, and any quantity with those two operations
propagates the same way. With combination as maximum and compounding as addition the recursion
is the critical path method. With other pairs it is cost roll-up or route selection.
Max-plus linear
systems theory treats the classical forward and
backward passes as linear algebra over an idempotent semiring, with the backward pass arising
as residuation \cite{baccelli1992sync}. A forward recursion exists for any pair of operations,
but a backward one is a property the pair either has or lacks, and this is the discipline
Chapter~\ref{ch:critical-path} adopts.

\section{Representing Uncertain Inputs}
\label{sec:bg-uncertainty}

The methods reviewed so far take a component failure probability, an edge capacity and an
activity duration as known numbers. In practice each is estimated from sparse failure data,
elicited from expert judgement, or quoted as a manufacturer's tolerance. Chapter~\ref{ch:main-intro}
distinguished aleatory uncertainty, the variability of a quantity across a population or over
repeated trials, from epistemic uncertainty, a lack of knowledge about a quantity that more
data would reduce. Probability theory is the accepted framework for the first. For the second
it is less satisfactory, because it requires a precise probability to be assigned even when the
evidence supports only a range, so that a quantity about which little is known is modelled in
the same way as one that is known well. Generalised probabilistic methods have been developed
to describe epistemic uncertainty with fewer assumptions, and they can be applied to any
computational model without modifying it.

\subsection{Intervals and probability boxes}
\label{sec:bg-pbox}

An interval $[\underline{x}, \overline{x}]$ states that a quantity lies between two bounds and
states nothing else. It is the appropriate form when a datasheet gives a tolerance or when a
value is known only to a measurement precision. Interval arithmetic returns an enclosure of the true range of a function over the interval
inputs. The enclosure is exact only when each input variable appears once in the expression.
Otherwise the arithmetic treats repeated occurrences as if they were independent, and the
enclosure is wider than the true range. This is known as the dependency problem. For a function that is monotone in each of its inputs the exact range
is available without interval arithmetic at all, from two evaluations at the lower and upper
corners of the input box. This observation is used in Chapters~\ref{ch:probability-toolkit}
and~\ref{ch:critical-path}.

A probability box, or p-box, bounds a distribution instead of a value. Following Ferson et
al.\ \cite{ferson2003constructing}, a p-box on a random variable $X$ is a pair of cumulative
distribution functions $\underline{F}$ and $\overline{F}$ with
$\underline{F}(x) \le \overline{F}(x)$ for all $x$, together with optional constraints on the
moments and on the family of the distribution. A distribution $F$ belongs to the p-box when
$\underline{F}(x) \le F(x) \le \overline{F}(x)$ for all $x$, its mean and variance lie in the
stated intervals, and it belongs to the stated family if one is given. When the two bounding
functions coincide the p-box is a single distribution and represents aleatory uncertainty
alone. When they are the step functions at the two ends of an interval the p-box is that
interval and represents epistemic uncertainty alone. Between these two cases the p-box carries
both. A p-box therefore covers the situation of a distribution whose family is known but whose
parameters are not, and the situation of a distribution estimated from samples measured with
limited precision.

Williamson and Downs established the arithmetic of p-boxes \cite{williamson1990probabilistic}.
For two random variables with p-boxes $A$ and $B$ and a binary operation, the p-box of the
result depends on what is known about their dependence. Under independence the result is a convolution of the bounding functions, evaluated on a
discretisation of each into a fixed number of levels, so that the cost of every operation
grows with the discretisation. Under no assumption about dependence the result is obtained
from the Fr\'{e}chet--Hoeffding inequalities, which bound the joint distribution of any pair of
random variables by functions of their marginals alone. The Fr\'{e}chet bound is valid whatever the true dependence and is therefore sound. For the
same reason it is wider than the independence bound. Which of the two applies at a given step depends on whether the quantities
being combined are functions of disjoint sets of underlying variables, and this question
governs the p-box propagation of Chapter~\ref{ch:probability-toolkit}. Software for p-box
arithmetic exists in R \cite{ferson2019pbar}, Python \cite{gray2022pba} and Julia
\cite{gray2021pbajulia}; the Julia library is one of the libraries this framework builds on.

\subsection{Neighbouring theories}
\label{sec:bg-other-theories}

Two other theories represent epistemic uncertainty without a precise probability assignment.
Fuzzy set theory represents a quantity by a membership function, assigning each possible value
a graded degree of membership instead of a frequency \cite{zadeh1965fuzzy}, and possibility
theory develops the same idea into a pair of measures, possibility and necessity. Evidence
theory, also called Dempster--Shafer theory, assigns belief mass to sets of values directly and
combines evidence from independent sources without assigning a probability to individual
outcomes \cite{shafer1976mathematical}; its belief and plausibility functions bound the
probability of an event from below and above. Both theories can be placed within the wider
field of imprecise probability, and a Dempster--Shafer structure on the real line can be
converted to a p-box and back. Neither theory is used in this thesis. The
quantities propagated here are probabilities, capacities and durations. The information
available on them in practice is stated directly as an interval or a p-box without
translation into membership functions or belief masses. In addition, the operations the framework performs on
its values are products, complements and weighted combinations, for which the p-box arithmetic
above gives results that are again p-boxes, so the same representation is carried from input to
output without conversion.

\subsection{Imprecision in the three analyses}
\label{sec:bg-imprecision-domains}

The exact reliability methods of Section~\ref{sec:bg-reliability} all consume a point-valued
component probability, and none of them propagates an interval or a p-box natively. For
example, an interval query against a decision diagram means evaluating the diagram at chosen input
corners, and there is no analytic route from a diagram to a bound on a distribution. In flow
analysis, Section~\ref{sec:bg-flow} showed the two established responses to uncertain
capacities, the adversarial uncertainty set of robust optimisation and the point-valued
discrete random variable of stochastic-flow reliability, and neither is an interval or a p-box
in the sense above. In scheduling, the interval treatment of durations exists and its
complexity is known, and the difficulty is confined to the backward quantities. Across the
three analyses, the same small set of representations recurs, point values, distributions,
adversarial sets and intervals, but no single representation is used consistently across all
three. Each analysis developed its own treatment of uncertainty independently of the other two.

\section{Multi-Analysis Tools for Complex Infrastructure}
\label{sec:bg-frameworks}

The same network is often analysed for several different behaviours, and several engineering
software tools run more than one kind of analysis against a single network representation.
\texttt{pandapower}, an open-source power-system tool, runs power flow,
optimal power flow, state estimation, topological graph search and short-circuit calculation
against one explicit graph of buses, lines and transformers, a range of analyses matched by
commercial suites such as DIgSILENT PowerFactory and PSS/E \cite{thurner2018pandapower}. The
ArcGIS Utility Network models power, gas and water networks as a graph of features connected
through topology and runs eight distinct trace types, connectivity, isolation, subnetwork
discovery and loop detection among them, against that shared topology
\cite{esri_utilitynetwork}. Neither tool's analyses are source-to-node reliability,
capacitated flow or activity scheduling, and neither propagates interval or p-box uncertainty.

Whether an existing tool or method combines these three analyses specifically, on one network
representation, is a narrower question. A search for such a tool found three partial answers
among tools and methods and one comparable piece of doctoral research, and none of the four
meets the description fully.

Commercial reliability software has, in practice, paired reliability with flow. Several of the
block diagram and fault tree suites in active use, ReliaSoft's BlockSim, Isograph's
Availability Workbench and ITEM Software's ITEM ToolKit among them, bundle a throughput or
process-flow module alongside their reliability engine
\cite{reliasoft2024blocksim,isograph2024availability,itemsoftware2024toolkit}. These modules
model multi-flow-type capacity, bottlenecks and resource allocation on the same diagrams the
reliability analyses use. None of their
public documentation describes a project-scheduling or critical-path module, and all three
represent component life and failure with classical distributions, fitted from data or
specified by the analyst.

Open-source infrastructure simulation platforms have paired flow with a form of
scheduling. InfraRisk integrates power-flow, water-hydraulic and traffic-flow simulators for
interdependent power, water and road networks under a resilience framing
\cite{balakrishnan2022infrarisk}. Its recovery module sequences repair-crew actions with start
and end times computed from travel time and repair duration, by heuristic prioritisation or by
model-predictive-control optimisation. This sequencing is a logistics schedule, since it
optimises the order and timing of repair actions against a performance-loss metric. It is not a
critical-path computation over a fixed activity network. Similarly, its reliability side is not
a source-to-node reachability computation. The hazard module derives point component-failure
probabilities from exposure and intensity to drive Monte Carlo disaster scenarios, and the
platform reports its results as simulated performance loss.

A third direction pairs reliability with schedule directly, inside project-network reliability
itself. Modelling a project's activities as the arcs of a multi-state network and asking for the
probability that the project completes within both a time and a budget constraint is an
established line of work. Huang, Huang and Lin compute this project reliability exactly. The space of feasible
completion-time and budget combinations is split into subsets via the project's upper and lower
boundary points, each subset is evaluated by inclusion-exclusion, and the method is validated
against full enumeration on a thirteen-activity manufacturing project \cite{huang2020exact}.
However, the method has no notion of a physical arc capacity carrying a transportable flow,
since activity duration and cost stand in its place, and every input is a discrete state with a
fixed probability.

Tong's doctoral thesis comes closest to combining two of the three exactly. The author
develops new methods for infrastructure flow networks and investigates their reliability in
terms of both connectivity and flow capacity, using the probability propagation method
reviewed in Section~\ref{sec:bg-reliability} \cite{tong2021infrastructure}.
Schedule and critical-path analysis are absent from it, and the probability treatment
throughout is point-valued.

No candidate reviewed above combines all three analyses on one network. Commercial software
pairs reliability and flow, with no schedule dimension. Open-source simulation platforms
combine flow and a form of scheduling without formal reliability computation. Project-network
theory brings together reliability and schedule; it has no flow network. Tong's thesis
reaches reliability and flow again, this time exactly, and omits schedule entirely. Every
one of the four represents its uncertain inputs precisely or adversarially.

\section{Delivery of Engineering Analysis Software}
\label{sec:bg-delivery}

The gap between an analysis existing in a library and an engineer being able to use it is
sometimes referred to as the last-mile problem \cite{hannay2009scientists,prabhu2011survey}.
Engineering analysis software is generally delivered to its users in one of three ways, as a
browser-based service, as a licensed desktop installation, or as a web-based geographic
information system. None of these is what the business-software industry calls no-code, and
this section reviews all four.

The no-code and low-code software category defines itself around business application
development. A systematic review of 383 definitions across 306 publications from 2014 to 2025
characterises no-code platforms as visual, drag-and-drop environments that let a non-programmer
build software without writing code, and low-code platforms as the same idea with a
professional-developer audience layered on top \cite{abendroth2026democratization}. The same review maps the identified platforms onto ten functional classes, such as
enterprise resource planning, customer relationship management and business process
automation, with commercial examples including Salesforce and UiPath. Engineering or
scientific analysis does not appear among them.

Within engineering analysis, browser-delivered simulation as a service is one established
pattern. SimScale, launched in 2013, runs computational fluid dynamics, finite element, thermal
and electromagnetic analysis in the browser with no local installation \cite{simscale}, with the
computation running in the vendor's cloud. The licensed desktop suite is a second and older pattern. The commercial reliability
software named in Section~\ref{sec:bg-frameworks} requires no programming and runs as a
local installation, so it has the local computation that SimScale lacks and lacks the
browser delivery that SimScale has. Web-based
geographic information systems are a third. A PRISMA-based systematic review of web GIS for hazard and infrastructure risk assessment
screened 1{,}775 articles and admitted 65. It organises the field around themes including
visualisation, user-interface design and decision support \cite{daud2024webgis}. The platform of
Repetto et al.\ is a representative member \cite{repetto2018windgis}. It delivers wind
monitoring, forecasting and statistical risk mapping through a web GIS built on open
geospatial software, and it is operated by port authorities who never touch the underlying
numerical models.
Most platforms in this category address monitoring and forecasting. They do not perform a
structural reliability or component-failure computation. Similarly, network visualisation environments
such as Gephi \cite{bastian2009gephi} and Cytoscape \cite{shannon2003cytoscape} make graphs
visual and explorable but carry no quantitative reliability analysis. The analytical capability
lives in libraries, e.g.\ in Matlab \cite{opencossan2018}, R \cite{ferson2019pbar}, Julia
\cite{gray2021pbajulia} and Python \cite{gray2022pba}, which a non-programmer cannot use.

A separate obstacle is data sovereignty. The accessible form of modern software is the
web application, and the usual web application is a cloud service, which raises security and
custody questions for proprietary system models \cite{hashizume2013analysis}, and in domains
such as nuclear decommissioning is not acceptable at all. Local-first software keeps the
usability of the web while storing and computing its data on the user's own machine
\cite{kleppmann2019local}. SimScale is browser-based but not local; the desktop suites are
local but not browser-based; the web GIS platforms are browser-based but run on a remote
server. No tool found in this search combines browser delivery, no programming, and local
computation and data.

\section{Graph Tooling Across Languages}
\label{sec:bg-language}

General-purpose graph libraries exist in every language the work could have been written in.
MATLAB has offered shortest-path, maximum-flow, centrality, connected-component and
spanning-tree functions on its native graph classes since the mid-2010s
\cite{mathworks_graphalgorithms}, and R's igraph provides the same over one shared graph object
\cite{csardi2006igraph}. Python's NetworkX covers simple, directed and multi-edge graphs over
a single native numeric type \cite{hagberg2008networkx}, and Rust's \texttt{petgraph} is a
newer and smaller equivalent \cite{petgraph}. Julia's ecosystem, centred on \texttt{Graphs.jl}
and its satellite packages for weighted and property graphs, occupies the same position
\cite{bezanson2017julia}. Dedicated reliability tooling is rarer. R carries a package built for
structural reliability, computing system and survival signatures over a network's topology
\cite{aslett_reliabilitytheory}. No single Python package built for network reliability in the
block diagram, path-set or decision-diagram sense was found; the closest candidate,
\texttt{pgmpy}, is a general Bayesian-network toolkit. This is a gap in packaged tooling only, since network reliability is an actively reviewed field with applications across
communications, transportation and energy distribution \cite{gaur2021literature}. Furthermore, none of the packages named above, in any of the five languages, carries a native
notion of an interval- or p-box-valued edge or node, because none is built for propagating
uncertain quantities across a network. The reasons for choosing Julia, and the language features the implementation depends
on, are given in Chapter~\ref{ch:julia-package}.

\section{Summary}
\label{sec:bg-summary}

Network reliability, network flow and scheduling analysis developed separately, each with
its own exact methods and its own treatment of uncertain inputs. The
exact reliability methods are all exponential in some width of the network and all consume a
point-valued component probability. Interval and p-box representations of epistemic
uncertainty exist, with an established arithmetic, but are not propagated natively by any of
the exact methods reviewed. Several engineering software tools run more than one analysis on one network object, but
no tool, method or thesis found in this search combines
source-to-node reliability, capacitated flow and activity scheduling on one network
representation, and none of the closest candidates propagates imprecision. No engineering
analysis tool found combines browser delivery, no programming and local computation. The
framework developed in the following chapters addresses each of these points.
