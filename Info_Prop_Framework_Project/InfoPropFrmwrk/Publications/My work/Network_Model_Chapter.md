# Chapter 3 — Network Model

## 3.1 Introduction

Every analysis developed in this thesis — critical path scheduling, capacitated flow, and probabilistic reachability — is defined over the same underlying object: a directed acyclic graph. Before any of those analyses can be developed, it is necessary to be precise about what that object is, what its structural vocabulary means, and why a directed acyclic representation is the right choice for the class of problem this thesis addresses. This chapter provides that foundation. It does not address *how* a network description arrives in this form from raw infrastructure data — file formats, parsing, schema validation, and the concrete data structures used to hold a network in memory are the subject of Chapter 4 (Input Processing Module), which follows directly from this one and depends on the definitions given here.

**Structure of the chapter.** Section 3.2 gives the formal definition of the network model used throughout the thesis. Section 3.3 defines the structural roles a node can play within that model — source, sink, fork, and join — which recur, unchanged, in every subsequent chapter. Section 3.4 defines topological ordering and the associated notions of ancestry and descent that later chapters (in particular, diamond decomposition) depend on directly. Section 3.5 argues, from first principles, why the directed acyclic graph is the necessary and sufficient representation for the exact, single-pass propagation algorithms developed in this thesis, in contrast to representations that permit cycles. Section 3.6 discusses how real infrastructure systems come to be represented in this form. Section 3.7 closes the chapter by connecting its definitions to the input-processing pipeline of Chapter 4.

## 3.2 The Network as a Directed Acyclic Graph

**Definition 3.1 (Network).** A network is a directed graph $G = (V, E)$, where $V$ is a finite set of nodes and $E \subseteq V \times V$ is a set of directed edges. For an edge $(u, v) \in E$, $u$ is called the *tail* and $v$ the *head*; the edge is said to run *from* $u$ *to* $v$.

**Definition 3.2 (Path).** A path from node $u$ to node $v$ in $G$ is a sequence of nodes $u = n_0, n_1, \dots, n_k = v$ such that $(n_{i-1}, n_i) \in E$ for every $i = 1, \dots, k$. The path is said to *traverse* each edge $(n_{i-1}, n_i)$ and to *visit* each node $n_i$.

**Definition 3.3 (Acyclicity).** $G$ is acyclic if there exists no path from any node $v$ back to itself of length $k \geq 1$. A directed graph satisfying this property is a directed acyclic graph (DAG).

Every network considered in this thesis is assumed to be a DAG. This is a modelling choice, not an incidental property of the infrastructure systems studied — it is defended explicitly in Section 3.5 below, and its consequences (a well-defined topological ordering, guaranteed termination of propagation, an exploitable parallelism boundary) are exploited by every algorithm developed in later chapters.

Two further primitive quantities attach to nodes and edges, and are what the propagation algorithms of later chapters actually operate on:

- **Node quantities.** Depending on the analysis, a node $v \in V$ may carry a *prior* or *intrinsic* value — for example, a task duration in critical-path analysis, or an intrinsic operational reliability $R(v)$ in reachability analysis (Chapter 6).
- **Edge quantities.** An edge $(u,v) \in E$ may carry a value governing how a node quantity is transformed as it crosses that edge — for example, a dependency delay in critical-path analysis, a capacity bound in flow analysis, or a transmission probability $p(u,v)$ in reachability analysis.

The network's topology — $V$ and $E$ — is common to every analysis; only these attached node and edge quantities differ between analyses. This separation of *structure* from *analysis-specific parameters* is precisely what allows one network model to be reused, unmodified, across the framework's three propagation algorithms, and motivates the *unified graph object* introduced formally in Chapter 4.

## 3.3 Structural Roles: Sources, Sinks, Forks, and Joins

Four structural roles, defined purely from the topology of $G$, recur throughout this thesis and are used identically by every analysis.

**Definition 3.4 (Source node).** A node $v \in V$ is a *source* if it has no incoming edges, i.e. there exists no $u \in V$ with $(u, v) \in E$. The set of source nodes is denoted $S \subseteq V$.

**Definition 3.5 (Sink node).** A node $v \in V$ is a *sink* if it has no outgoing edges, i.e. there exists no $u \in V$ with $(v, u) \in E$.

Sources represent the points at which a network quantity originates — a project's starting tasks, a flow network's supply points, a reachability network's unconditionally operational entry points. Sinks represent the points at which it is ultimately observed — a project's completion milestones, a flow network's demand points, the nodes whose reachability is of interest. A network need not have a single source or sink; the framework's algorithms are defined for the general multi-source, multi-sink case throughout (see, for example, the super-source/super-sink reduction used in flow analysis).

**Definition 3.6 (Fork node).** A node $v \in V$ is a *fork* if it has out-degree greater than one, i.e. $|\{u \in V : (v,u) \in E\}| > 1$.

**Definition 3.7 (Join node).** A node $v \in V$ is a *join* if it has in-degree greater than one, i.e. $|\{u \in V : (u,v) \in E\}| > 1$.

Fork and join nodes mark, respectively, where a network's structure branches and where separately-branched paths reconverge. On their own, these are purely structural properties — the *identification* of fork and join nodes requires only in-degree and out-degree counting, and is common to every analysis in the framework (it is computed once, during the structural-analysis stage of the shared preprocessing pipeline described in Chapter 4). Their consequence, however, differs sharply by analysis. In critical-path and flow analysis, a fork/join pair is unremarkable: it is handled by ordinary maximisation (critical path) or the standard mechanics of network flow. In reachability analysis, by contrast, a join node whose incoming paths share a common upstream fork is the source of a specific and otherwise easily overlooked correctness hazard — the *diamond* structure — because the paths reconverging at such a join are not statistically independent of one another. This hazard, and the structural analysis needed to resolve it, is developed as its own, self-contained topic in Chapter 5 (Diamond Decomposition); the point to establish here is only that forks and joins are structural properties of the DAG itself, identifiable without reference to any particular downstream analysis, and it is exactly this analysis-independence that justifies treating diamond decomposition as a separate chapter rather than folding it into the reachability chapter that consumes it.

## 3.4 Topological Order, Ancestors, and Descendants

**Definition 3.8 (Topological order).** A topological order of $G = (V,E)$ is a bijection $\text{rank}: V \to \{1, \dots, |V|\}$ such that for every edge $(u,v) \in E$, $\text{rank}(u) < \text{rank}(v)$.

A topological order exists for $G$ if and only if $G$ is acyclic — this equivalence is the precise sense in which acyclicity (Definition 3.3) is not merely a convenient property but a necessary one for the propagation algorithms developed in this thesis, all of which require processing every node only after every one of its predecessors has already been processed.

**Definition 3.9 (Iteration sets).** A partition of $V$ into disjoint, ordered layers $I_1, I_2, \dots, I_k$ is an *iteration-set* decomposition if, for every edge $(u,v) \in E$ with $u \in I_i$ and $v \in I_j$, $i < j$. Equivalently, every node's immediate predecessors lie in strictly earlier layers than the node itself.

Where Definition 3.8 gives a total order over nodes, Definition 3.9 gives a coarser, layered order — nodes within the same layer $I_i$ have no dependency relationship between them and may, in principle, be processed in any order, or concurrently, relative to one another. This is the formal statement of the parallelism boundary claimed informally in Chapter 1: propagation *across* layers must respect dependency order, but propagation *within* a layer need not. Every propagation algorithm in this framework is structured as a single sweep over the iteration-set decomposition of the network, layer by layer; the concrete algorithm used to construct this decomposition (a depth-partitioned form of Kahn's algorithm) and the proof that it yields convergence in exactly $k$ layers are given in Chapter 4, where the decomposition is realised as a concrete data structure (the `iteration_sets` field of the unified graph object).

**Definition 3.10 (Ancestors and descendants).** The ancestor set of a node $v$, denoted $\text{anc}(v)$, is the set of all nodes $u \in V$ for which a path from $u$ to $v$ exists in $G$. The descendant set $\text{desc}(v)$ is defined symmetrically as the set of all nodes reachable from $v$.

Ancestor and descendant sets are computed once for every node, alongside the iteration-set decomposition, during the framework's shared structural-analysis stage (Chapter 4). They are used directly, and repeatedly, in Chapter 5: identifying whether two paths into a join node share a common upstream fork — the defining test for a diamond structure — reduces to an ancestor-set intersection test, and is the single most frequently executed operation in the diamond-identification procedure. Their inclusion in the shared network model, rather than being computed freshly by whichever analysis happens to need them, is a direct instance of the framework's central design principle: structural properties of the network that are independent of any specific analysis are computed once, in one place, and reused.

## 3.5 Why Directed Acyclic Graphs

The restriction to acyclic networks (Definition 3.3) is not adopted for mathematical convenience alone; it is what makes exact, single-pass propagation possible, and its absence would force every algorithm in this thesis to be replaced with an iterative approximation scheme of the kind this framework specifically sets out to avoid. Four consequences of acyclicity, informally introduced in Chapter 1, are stated here more precisely.

**Consequence 1 — a canonical processing order exists.** By Definition 3.8, acyclicity guarantees at least one topological order, and hence at least one valid iteration-set decomposition (Definition 3.9). Every propagation algorithm in this framework relies on the existence of such an order to guarantee that, when a node is processed, every value it depends on has already been finalised.

**Consequence 2 — propagation terminates in a bounded number of steps.** Because no path can revisit a node, the number of iteration-set layers $k$ is finite and bounded above by $|V|$; a single sweep over all $k$ layers visits every node exactly once and cannot re-enter a layer already processed. This is in direct contrast to networks containing cycles, over which propagation of a dependent quantity (a schedule, a flow, a belief) generally has no finite closed-form solution and must instead be approximated by iterating some update rule until it converges to a fixed point — with convergence itself typically requiring separate proof, and no guarantee of exactness at any finite iteration count.

**Consequence 3 — same-layer independence is an explicit parallelism boundary.** As noted under Definition 3.9, nodes within one iteration-set layer have no dependency relationship with one another. The reachability algorithm developed in Chapter 6 exploits this directly: root diamonds are processed level-by-level, with diamonds *within* a level dispatched to concurrent worker threads, precisely because the acyclicity of the network guarantees that no such diamond can depend on the result of another diamond in the same layer.

**Consequence 4 — a single forward (and, where needed, backward) pass suffices for exactness.** Because dependencies in a DAG never cycle back on themselves, every quantity computed by the algorithms in this thesis — a critical-path completion time, a maximum flow value, a reachability probability — is obtained by a single topologically-ordered sweep (forward for critical-path early-start and reachability propagation; forward followed by a reverse sweep for critical-path late-finish and slack). No algorithm in this thesis relies on iterative convergence to a numerical tolerance; every result reported is exact given its inputs.

These four consequences are the technical justification for treating the DAG not merely as one convenient representation among several, but as *the* representation this framework is built around, and for making acyclicity a validated precondition — rather than an assumption — of the input-processing pipeline described in the next chapter.

## 3.6 From Infrastructure Systems to Directed Acyclic Graphs

The infrastructure systems this thesis is concerned with are not, in general, presented to an analyst as an abstract graph; they arise as physical or organisational systems whose dependency, flow, or precedence structure must first be identified and then oriented into the directed form of Definition 3.1. Three broad classes of systems, drawn on throughout this thesis's case studies, illustrate how this orientation arises naturally from the system's own semantics rather than being imposed on it:

- **Precedence networks.** In project scheduling, an edge $(u,v)$ represents the constraint that task $v$ cannot begin until task $u$ has completed. The direction of the edge is fixed by the precedence relation itself, and acyclicity is a precondition for the schedule to be executable at all — a cyclic precedence constraint would describe a set of tasks each waiting on the others, which cannot be scheduled. This class underlies the critical-path case studies of Chapter 7.
- **Physical flow networks.** In distribution infrastructure — water, gas, or drone-logistics networks — an edge $(u,v)$ represents a physical conduit or route along which material or vehicles may move from $u$ to $v$. Direction is fixed by the physical or regulatory constraint on flow (a one-way route, a gravity-fed pipe, a directed drone corridor); where flow can genuinely occur in either direction along a physical link, this is represented, not by an undirected edge, but by a pair of opposing directed edges, preserving the directed-graph formalism throughout. This class underlies the flow-capacity case studies developed in the companion Flow Toolkit chapter.
- **Failure-propagation networks.** In reliability analysis, an edge $(u,v)$ represents that the operability of $v$ depends, in part, on $u$ remaining operational and the connection between them remaining intact — for example, a downstream substation's dependence on an upstream feeder. Direction here follows the direction of operational dependency, not necessarily the direction of any physical flow. This class underlies the reachability case studies of Chapter 6, which include a power-grid-style benchmark network and a family of drone medical-logistics network designs.

In each case, the acyclicity of the resulting graph is not an artefact of convenient case-study selection; it follows from the semantics of the relation being modelled — a precedence constraint, a physical flow direction, or a dependency relation — each of which is inherently a partial order (or reduces to one once genuinely bidirectional links are split into opposing directed edges), and a finite partial order is, by construction, acyclic.

## 3.7 From Network Model to Input Processing

This chapter has defined the network model — a directed acyclic graph, together with its source, sink, fork, and join nodes, its topological iteration-set decomposition, and its ancestor/descendant relations — that every subsequent chapter of this thesis takes as given. It has not addressed how a network described in some raw, heterogeneous infrastructure data format (an edge-list file, an adjacency matrix, associated JSON metadata describing node priors, edge capacities, or task durations) is parsed, validated, and assembled into a concrete realisation of this model in software, nor the specific data structures used to hold that realisation in memory. That is the subject of Chapter 4, which develops the framework's *unified graph object* as the software-level realisation of the mathematical model defined here, and the input-processing pipeline that constructs it — including a formal proof that the topological iteration-set construction outlined informally in Section 3.4 above converges in exactly $k$ iterations, where $k$ is the number of layers in the decomposition.
